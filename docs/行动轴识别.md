# 行动轴识别（原 E 线）

> 本文合并了原来 3 篇（`行动轴识别_交付` / `实机HUD框偏差_诊断` / `实机抓屏核对`），
> 并**去掉了调查过程**（诊断结论已固化进正文）。
> 用户口径与铁律见 [`用户口径与铁律.md`](用户口径与铁律.md)。

**一句话**：读屏幕上**左侧行动轴顶端那张卡**，判断"现在是谁在行动" ——
顶端槽**位置固定**，多模板 NCC 分类，两道闸（分数 + 分差），判不出来就「待复核」。

## 0. 现状指标（实测）

| 项 | 结果 |
|---|---|
| **顶端槽位置** | ✅ **固定** `(66,66)-(300,195)`；头像内容区 `(90,81)-(232,175)`；左标记中心 `(86,127)` |
| 单位分类 | 同类多模板取最大：灰度 NCC + 0.6×梯度 NCC + 0.3×色度(Lab a/b) NCC |
| **8 个单位类留一帧** | **97.2%（69/71）**；分数过阈值的帧里**正确率 100%** |
| **非我方帧**（敌人/空/过渡）| 最高分 0.89 → 阈值 0.90 → **零误报** |
| **两道闸** | 分数 ≥ **0.90** 且与第二名分差 ≥ **0.45**，否则「待复核」 |
| 速度 | **~1 ms/帧**（内存图；含标记匹配约 7 ms）|
| 分辨率 | 按宽度等比缩放：2876×1798 / 2870×1800 都可用（自检含 0.5x/0.75x/1.5x）|
| 覆盖率（录屏1，249 帧）| 90 帧给出结论；其余多为**动画期间整条行动轴被隐藏**、敌人回合、过渡帧 |

## 1. 几何（硬事实，别再重新验证）

* **顶端槽固定**：框内永远是"当前行动者"那张卡。
  队列**下面**那些卡确实会滚动，但**顶端那张不动** → "时间平均/固定网格失效"只对下面成立。
  > ⚠️ 历史教训：旧方案用**全图多尺度滑窗**是绕远路，也正是"昔涟↔长夜月系统性混淆"的来源。
* **卡面有两种渲染**：相差 **1.08 倍缩放 + (4,2)px 位移**
  （同一张图跨渲染 NCC 0.88，不同角色只有 0.50）→ 模板库按两种缩放各存一份
  → 覆盖率 94%→96%，精度不变。

## 2. 左边界标记：**形状编码"行动类型"、颜色编码"阵营"**

| 形状 | 含义 | 关键证据 |
|---|---|---|
| **圆点 `dot`** | 按行动值排队的**正常行动** | 死龙/长夜（自带速度、进行动序列）33 帧全点 |
| **四角星 `star`** | **插入行动轴的行动**（立即行动/额外回合/欢愉技插入）| 小伊卡/德谬歌（速度 0、**不进行动序列**）38 帧全星；同一角色两种都出现过（昔涟 t=116 点 / t=129 星）|
| **菱形 `diamond`** | **机制/技能卡**（不是单位卡）| 欢愉技『?』卡（青色）、敌方机制卡（红色）|
| **金环套金星 `gold_aha`** | **阿哈时刻面具框** | 录屏2 t=20~33、68、110、163、182、221、292、311、338 |

* **颜色**：**青 = 我方、红 = 敌方、金 = 阿哈时刻**。
  ⚠️ 色相分不开"阿哈金"和"敌方红"（都在 H 0~15）→
  **形状靠模板分数分类，颜色只用于命名**。
* ⚠️ **"金环"和"金星"是同一个字符**，不是两种状态：阿哈卡的标记 = 金色圆环 + 环里一个**脉动**的四角星。
  证据：`images/E2_aha_glyph.png`（0.2s×14 帧连拍）；量化：阿哈环↔星相似度 1.46~1.54（同一字符），
  而我方圆点↔星只有 0.84~0.98（不同字符）→ 已合并成一类 `gold_aha`，判别 14/14。
* ⚠️ 同一个标记在**亮到发白的卡面**上会被背景吃掉（录屏2 t=12/53/95 的星被判成点）——
  这是我方点/星判别的**主要错误来源（≈91%）**。

## 4. 欢愉玩法 / 阿哈时刻（录屏2，2870×1800）

* **阿哈时刻期间顶端槽被阿哈时刻卡占据**：金色面具框 + 一个**成员头像** + 右侧成员队列条。
* 框里头像**逐个切换**，0.2s 抽帧实测**每个成员约 1.2 秒**
  → 每个头像 = 该成员的一次**欢愉技（插入行动）**。
* 另有青色菱形的 **『?』卡** = 欢愉技卡本身，也占顶端槽。
* 全程 **9 段**阿哈时刻、每段 8~25 秒，**合计占 36% 时长**（419 帧里 `card_type=aha` 163 帧）。

## 7. ⭐ 给归属引擎的接法（**关键**）

用 `out/axis_actors_E.csv`（列：`t,unit,owner,score,margin,marker,inserted,card_type`，判不了就是空串）。

### ⚠️ **不要用"事件那一帧"单帧定归属**

HUD 数字是**打完之后**才出现并停留 ≈0.5s，而顶端卡在这期间**可能已经上移/换人**。

**推荐规则**（`tools/axis/event.py` 已实现）：以事件时刻为基准，
在 **[-1.5s, +0.5s]** 内取**最近的已确认帧**，**优先取事件之前的**（先动手、后出数字）。

> 反例实测：读数 `32209` 在 t=221（顶端昔涟）与 t=222（顶端长夜月）都在，
> 允许"取之后"就会判成长夜月（**错**）。

实时 30fps 用 `read_window(frames, min_votes=n//3)` 投票。

### `card_type` 要特判

| card_type | 处理 |
|---|---|
| `aha` | 顶端是阿哈时刻面具框 → **行动者 = 框里那个头像对应的成员**（不是普通单位卡）|
| `elation` | 顶端是欢愉技『?』卡 → 同样按"卡上是谁"归属，判不出来标待复核 |
| `enemy` / `empty` | **不是我方，跳过** |

`inserted=True`（四角星）= 这次是**插入行动轴的行动** → 用于判断"HUD 增量是不是一次完整新行动"。

## 8. 铁律与已知限制

### 8.1 铁律

1. ⭐ **宁可漏，不要错**：判不出来返回 `unit=None`（"待复核"），
   **不要用第二名的类名凑答案**。过渡帧第二名离得很近（实测 t=294 间距仅 **0.013**），凑了就是错。
2. **用户的标注/读数是唯一真值来源**；不要用在线大模型识别。
3. **改参数后必须跑回归**：`python axis_actor.py --selftest`（18 条真值帧 + 3 档分辨率缩放）。
4. **给用户看图**：不超过屏幕尺寸、不超出画布、**不用颜色编码**（只用文字标签）。
5. 帧号格式化用 `T.fmt_t()`：抽帧缓存里有 `f00135.10~90` 这种 0.1s 帧，
   用 `%.0f` 会把 t=135.6 显示成 136（踩过一次）。

### 8.2 已知限制（诚实清单）

* **动画期间整条行动轴会隐藏**（大招等），此时顶端是空的 → 事件那一帧经常取不到人，
  必须看邻帧（见 §7）。这是用户反馈的"**开大把行动轴踢出去**"现象，诊断见
  [`附伤与开大踢轴.md`](附伤与开大踢轴.md)。
* 过渡帧（卡在滑动/被白色特效盖住）会被判「待复核」：**这是设计取舍，不是 bug**。
* **只识别顶端一张**。整列队列（下面 11 张 + 行动值数字）**没做**；归属只需要顶端。
* **只支持整屏等比缩放**的抓屏；窗口裁剪/非等比缩放会导致坐标错位。
* **单位模板库已扩到 109 角色 / 2372 帧**（见 [`任意队伍适配.md`](任意队伍适配.md)）。
* ⚠️ **已知边界帧 `t=159`**：期望长夜月，实得待复核
  （长夜月 1.253 vs 三月七·巡猎 1.024，间距 0.229 < 0.45）。
  **扩容前（备份库 36 条目）间距 0.303，本来就不过闸** → 不是扩容引入的。
* **跨形态泛化弱**：同一角色的不同形态靠 NCC **泛化不动**
  （实测整组留出只 10.8%）→ 正确用法是**把每个形态都在指认图上报同一个名字**。

## 9. ⭐ HUD 框的实机偏差（**踩过的大坑，务必读**）

### 9.1 现象

用户屏幕 **2880×1800**、DPI 192（200%），与录屏参考（2876×1798）只差 **0.14%** ——
**尺度不是问题**。但实机数字实测在 `y≈298~358`，而静态模型框是 `y 260~340`：
* 顶部装进了「总伤害」标签
* **底部（340）切掉数字下半（→356）**

用户判断："**不同模式下总伤位置不同**" —— **是对的**。

### 9.2 为什么"等比缩放"救不了

等比缩放的前提是"**同一 UI 在不同分辨率下等比布局**"。但两个画面**分辨率几乎相同**、
位置却差 30px → 这是**模式/布局差异**，不是分辨率差异，缩摆放不了。

### 9.3 ⚠️ 一个反直觉的实测结论

| 组合 | 与离线权威表不同的帧数 |
|---|---|
| 墨迹定位框（线7 `hud_geometry(rgb)`）| **68 / 923** ❌ |
| **参考框（按分辨率等比缩放）** | **0 / 923** ✅ |

**根因（很重要）**：线7 的墨迹框**同时给出了偏移的 `bar_rows`**：
```
参考:      box=(260,2350,340,2876)   bar_rows=(298,310)
线7 墨迹:  box=(257,2074,380,2876)   bar_rows=(315,333)
```
`bar_rows` 是"装饰金线行带"，**分割前要挖空**（否则金线会把最左数字粘住）。
一旦它**跟着框下移**，就会**压在数字自己的笔画上** → 笔画被当金线挖掉 → **字被切碎 → 丢前导位**。

### 9.4 ⇒ 正解：**只动态定位，不动态挖空**

```
① HUD 抓屏矩形 → 动态定位（用字体档案 HP.box_for）
② bar_rows     → **不跟着平移**（或与框成对平移，且必须验证）
③ 宽度         → 按实测字号给足容量（12 位）
```

**已验证的正确路径**：`hud_profiles.box_for('default', 整帧)`
→ 实机得到 `(285,2353,365,2880)`、`bar_rows=(323,335)` → 读出 `73431`（与屏幕一致）；
而静态框读出 `53438`（**错**）。

### 9.5 实机抓屏的其他事实

| 项 | 值 |
|---|---|
| 整屏 | **2880×1800**，DPI 感知**必须开**（不开时逻辑 1440×900 → 抓错地方）|
| HUD 区 | 用户确认过：实机下**必须动态定位**（见 §9.4）|
| 行动轴区 | 基本正确（覆盖卡片列，右缘可能略窄）|

> ⚠️ **一个方法论教训**：截图工具 `BitBlt`/`mss` **抓不到 layered 窗口**，
> 所以"截图里看不到悬浮窗"**证明不了**它没显示；要用 `PrintWindow` API 或直接看屏幕。

## 4. HUD 数字区：从"黄色墨迹"反推裁剪框

### 4.1 算法（每一步都是被实测逼出来的）

1. **搜索窗** = 右上角一条带（`y ≤ 0.32H`、`x ≥ 0.60W`）——与分辨率无关的先验：HUD 锚在屏幕右上角；
2. **掩膜** = 淡黄辉光 ∪ 饱和黄核心（`hud_glyphs.locator_masks`，**与提取完全同一套阈值**，
   否则会出现"框定在一个地方、字却切不出来"的鬼故事）；
3. **行带**：按行统计墨迹像素，取 `≥ 帧宽×0.02`（≈58px）的行 → 实测录屏1 稳定得到 **61px 高**的行带
   （273..333）；这个阈值正好把光晕尾巴与淡金线裁掉；
4. **候选筛选**：字号比必须落在 `[0.6, 2.6]×分辨率系数`，且行带**右缘贴屏右缘**（≤70px）
   → 取墨迹最多的那条（数字串的墨迹远多于飘字/特效形成的条带）；
5. **列链**：行带内按列取段、从最右一段向左链式合并（空隙 ≤30·k）→ 单字宽高比过滤；
6. **出框**：`y0 = 行带顶 − 13·k`、`y1 = 行带底 + 7·k`、右缘**贴屏右缘**（HUD 右对齐，
   末位是 `1` 时墨迹右缘会窄 8px）、左界 = 右缘 − `526·max(k, 分辨率系数)`（12 位容量，按字号放大）。

### 4.2 为什么不用"连通块 + 右对齐链"（一开始就是这么写的，实测翻车）

装饰金线**横穿**数字时（录屏1 `t=141.8`），会把每个字切成上下两半：

* 上半块/下半块的宽高比 ≈1.8，被"单字宽高比"过滤掉 → 只链到最右 4 个字；
* 字号被估成 **0.93**（真值 1.52）→ 框 `(282,2376,357,2868)`，比人工框**低 22px**。

改成"行带 + 列链"后，`t=141.8` 正确给出 `(257,2074,380,2876)`（k=1.52）——因为**列剖面天然不受
横穿金线影响**（一个字的列在挖空金线行之后仍然有墨），这也正是 A 线提取器 `BAR_ROWS` 的同一思路。

### 4.3 实测（`out/l7_accept.txt`）

* **录屏1 参考字号帧（16 帧）**：自动框 vs 人工框 `(260,2350,340,2876)` → **四边最大偏差 1px**
  （13 帧逐边完全一致，3 帧差 1px：行带边界 ±1px 的测量噪声）。
* **录屏2（字号 1.52 倍）**：自动框 `(257,2068,380,2870)`；人工按同一条边距规则从放大网格图上量的框
  `(257,2060,381,2870)` → y 两边 **≤1px**、右缘贴屏一致、左界宽 8px。
  左界是"容量"不是"墨迹边"：12 位需求 = 12×55+50 ≈ 710px，自动框宽 802px（够用且留余量），
  8px 的差来自字号估计（94/61=1.54 vs 自动测的行带 93/61=1.52），**宁可宽不可窄**
  （录屏2 原先就是被窄框切掉最高位的，见 `docs/HUD数字读取.md`）。
* **录屏1 的大字号帧**（`t=134.8/141.8/229.8/252.2`，k≈1.5）：自动框 `(257,2074,380,2876)`；
  A 线老框 260..340 **装不下**它们（墨迹底 369 > 340）。这是顺带发现的事实，供线2 参考。

### 4.4 与 A 线的关系（回归证据）

A 线留出集 5 帧（226/261/275/284/311）在**动态框**下：逐字 **29/29**、整串 **5/5**（基线也是 29/29、5/5）。
另外做了敏感度实验：把框整体平移 ±3px（含左右），留出集**仍然 29/29** —— 说明 A 线读数对几像素的
框抖动不敏感，动态框不会把 A 线弄坏。

## 5. 行动轴顶端卡：模型先验 + 证据纠正

### 5.1 为什么要这样（而不是全图找卡）

实测发现：**轴会整体滑入/滑出**。`t=106` 时顶端槽是空的，第一张卡在 y≈180（比标定位置低约 100px）；
`t=135/153/261` 整条轴不可见。如果去全图找"最上面那张圆角矩形"，这些**过渡帧**会被判成"当前行动者"，
直接违反 E 线"宁可漏不要错"的铁律（也会污染事件表）。

所以定位的是**槽**，不是"画面里最上面的卡"：

* **模型（先验）**：卡左边框 `88·s`、上边框 `80·s`（`s = 帧宽/2876`）。等比缩放下这是精确的；
* **证据**：
  * 卡上边框"脊"——比上下各 9·s px 都亮的一条横线（实测真卡峰值 78~81，分数 8.5~108；背景 ≤2）；
  * 轴面板左缘竖线（实测 x=55 = 卡左边框 −33；面板隐藏时它消失）；
* **默认只校验，不顶掉模型**（`refine=False`）：证据与模型相差 >4px 时返回 `suspect=True`，
  框仍是模型值；要真的用证据纠正得显式 `refine=True`。

**为什么默认不顶（这是本线最重要的一个取舍）**：把 `refine` 打开后重出 E 线 CSV，
255 行里有 **5 行**变了（`t=194/237/256/306/322`）。最坏的一例 `t=194`：卡上方有一条**亮特效带**，
脊检测器把它当成"卡上边框"（分数 20，而卡自己那条边框只测得 3）→ 框上移 22px →
一次**本来判对的『死龙』**变成待复核。也就是说：**这条通路会改 E 线的输出**，
而 E 线 CSV 是线4/线8 事件表的上游。本线的验收里没有"改 E 线行为"这一项，
所以默认关掉纠正、只把证据留成可观测的字段（`suspect`/`ridge`/`rail`），
把"能改"这件事用合成用例证明（§5.3）。

### 5.2 为什么阈值是 4px（有实验依据，不是拍的）

把 `TOP_ART` 整体平移后重跑 E 线 18 条真值帧：

| 平移 | 判定正确 | 最低正确分 |
|---|---|---|
| −3 / −2 / −1 / 0 / +1 / +2 / +3 px（上下或左右） | **18/18** | 1.42~1.90 |
| −4px（左右） | 17/18（`t=221` 变待复核） | 1.42 |
| +4px（左右） | 17/18（`t=109` 变待复核） | 1.33 |

→ **±3px 是安全区，±4px 开始翻车**。这正好解释了验收为什么定 ≤3px，也是"≤4px 就认为证据与模型一致"的来历。

### 5.3 实测

* 录屏1 **31 帧**、录屏2 **6 帧**：`top_art` 与人工标定 `(90,81,232,175)` **全部 0px 偏差**、标记中心 `(86,127)` 一致；
* 其中 17 帧证据过阈值且与模型一致（脊 78~81 / 竖线 55）；10 帧落在滑入/滑出动画里（无证据）→ 用模型；
  5 帧证据与模型差 >4px → `suspect=True`，**不改框**（`t=194/237/256/306/322`）；
* **证据纠正通路**的合成用例（把轴整体下移 20px，`refine=True`）：脊测到 y=99（分数 60）
  → `src=detect`、`top_art` 跟着走，说明"模型错了会改"这条通路是通的（不是永远返回常量）。
* **下游零影响**：`refine=False` 下重出 `out/axis_actors_E.csv`，与旧表在共同的 255 个时刻上
  **逐字段 0 差异**。（复现：`python tools/axis/export.py --out /tmp/new.csv --no-accept` 后按 `t` 对比。）

## 7. 怎么接（给 A / B / E / 线5）

```python
import geometry as SA

# ① 实时线开跑前：探测 + 定位（一次）
info = SA.probe_display()                    # {'screen':(2880,1800),'dpi':192,'scale':2.0,...}

# ② 抓一张整屏 → 算出该抓的两块区域 → 之后只抓这两块

with Grabber() as g:

    hud  = g.grab_hud()                      # RGB ndarray，区域已按画面定位

# ③ 离线/单帧：直接问几何
g = SA.hud_geometry(rgb)                     # {'box':(y0,x0,y1,x1),'bar_rows':(a,b),'k':..,'src':'ink'|'model'}
a = SA.axis_geometry(bgr)                    # {'top_art':(x0,y0,x1,y1),'mark_c':(x,y),'mark_r':19,
                                             #  'src':'model'|'detect','suspect':bool,'ridge':..,'rail':..}
a = SA.axis_geometry(bgr, refine=True)       # 要"证据顶掉模型"就显式打开（默认关，见 §5.1）

# ④ A 线：什么都不用改 —— hud_glyphs.extract() / hud_profiles.glyphs() 默认就走动态定位
```

`axis_actor.read_actor(..., geom=...)` 就是为这个留的（不传则每帧现算，离线/评估用）。

## 8. 已知限制（写清楚，别猜）

1. **非等比缩放（换宽高比）**：HUD 跟得上；行动轴仍是帧宽等比模型（E 线的口径，不属本线）。
2. **像素字体档案（银狼999）不参与动态定位**：它用青绿掩膜，本线的"黄色墨迹定位器"不适用；
   `hud_profiles` 里该档案 `locate=False`，仍用标定框。要适配得另写一套掩膜定位。
3. **E 线模板库仍从参考框裁**：模板是 E 线 97.2% 指标的根基，动它 = 动指标。
   推理侧走动态定位；两者在参考分辨率上给出的框**完全一致**（§5.3 的 0px 与 CSV 0 差异就是证据）。
4. **行动轴证据纠正默认关闭**（`refine=False`）：证据会跑偏的 5 帧里最坏一例会掉一次正确判定，
   而 E 线 CSV 是线4/线8 的上游 → 默认只标记不改框。要做实机自适应时再打开并重跑下游回归。
5. **证据搜索是有界的**：脊只在模型预测 ±25px 内找。模型偏差超过 25px 就纠正不了 ——
   这是有意的（宁可用模型，也不做全图搜索去找一张可能正在滑动的卡）。
6. **行带阈值是绝对量（帧宽×0.02）**：极大/极小分辨率下需要重新标定这个数（本轮没有那种素材）。
7. 录屏本身就是**裁过边**的（2876×1798 / 2870×1800 / 2878×1798 三个尺寸），
   所以"帧右缘 = 屏右缘"这个假设在录屏上成立，实机窗口化抓屏时不成立 —— 那时请用
   `hud_geometry` 的 `ink_x1 + 23k` 分支（`W - ink_x1 > 70` 时自动走这条）。
