# 实时链路与悬浮窗（原 B 线 + MVP + P1）

> 本文合并了原来 5 篇（`实时抓屏_交付` / `MVP_范围与验收` / `MVP_实施记录` /
> `实机读数可靠性_交付` / `EXE打包_专项记录`），去掉实施过程，只留结论与坑。
> 用户口径见 [`用户口径与铁律.md`](用户口径与铁律.md)。

**一句话**：整屏抓屏 → 读 HUD 数字 + 认行动轴顶端角色 → 流式切事件并归属 →
**置顶 + 鼠标穿透的悬浮窗**实时显示每个角色的累计伤害。

## 1. 实时链路架构

```
ScreenSource          一帧 → {hud_region, hud_top/left/bar, axis_rgb, axis_geom}
   ↓
Perceiver.read()      一帧 → 一条读数（HUD 数字 + 行动轴顶端行动者）
   ↓
LiveEngine.add()      流式事件引擎（滑动窗口重算 + **定稿延迟**）
   ↓
Overlay.update()      悬浮窗刷新（4 角色累计 + 占比 + 合计 + 当前行动者）
```

**模块对照**（现名 → 见 `代码改名_交付` 的新名映射）：

| 文件 | 作用 |
|---|---|
| `capture.py` | 抓屏（mss BitBlt + DPI 感知 + 区域缓存）|
| `mvp/reader.py` | 感知层：一帧 → 一条读数。**只做接口适配，不复制识别逻辑** |
| `mvp/engine.py` | 流式事件引擎：滑动窗口重算 + 定稿延迟；**直接复用 `events_v4` 的判据函数** |
| `mvp/overlay.py` | 悬浮窗（置顶 + 鼠标穿透 + 全局热键 + `--selftest`）|
| `mvp/live_mvp.py` | 主循环：实时抓屏 / 录屏回放**两种帧源、同一套下游** |
| `mvp/verify_live.py` | 离线对账 |
| `mvp/av_reader.py` | 「每行动值伤害」占位（恒返回 None → UI 显示 `—`）|
| `mvp/resource.py` | ⭐ 资源路径统一解析（源码 / exe 双模式）|
| `mvp/gui_launch.py` | **控制面板**（点「开始统计」）|
| `gui_main.py` | exe 入口：无参数弹 GUI，带参数透传给 `live_mvp` |

## 2. ⭐⭐ 实机三大坑（**最重要的一节**）

### 2.1 悬浮窗自己盖住行动轴 → 行动者全灭（**最隐蔽**）

**现象**：exe 在窗口化全屏下"数字一直不动"。

**实测产物**：
| 项 | 实测 |
|---|---|
| HUD 侧 | **完全正常**（读数在涨、框来源 `ink` 全程）|
| 事件 | 出了 10 条、数值都像样，但**全部 `status=review`** |
| **行动轴** | **判出行动者 0 / 380 = 0.0%** ← 卡在这里 |
| 悬浮窗 | 画在 `(40,40)`，**正好压住左上角的行动轴那一列**（x 60~340, y 0~1250）|

**机制**：抓屏是**整屏 BitBlt**（mss）→ 它会**连同我们自己的悬浮窗一起抓到**。
悬浮窗压住行动轴 → 顶端卡被自己的窗口挡住 → 认不出 → 每条事件都"判不出行动者"
→ 按铁律进 `review` → **合计恒 0**（而 HUD 数字其实一直在正常读）。

**修法**：`SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)`（= 0x11，Win10 2004+）
—— 悬浮窗**在屏幕上照常可见**，但**任何抓屏 API 都拍不到它**。

**对照实验**（同一台机器、同一套 mss/BitBlt）：
| | 抓屏里"悬浮窗底色"像素数 |
|---|---|
| 开启 | **20**（噪声）|
| 关闭 | **166,242**（整块都在）|

**副作用（要知道）**：开启后**用户自己的截图/录屏里也不会出现悬浮窗**（这正是它的作用）。
自检要存"悬浮窗长什么样"时会**临时**关掉 affinity 再截。

**兜底**：万一设不上，启动时若检测到"悬浮窗矩形 ∩ 行动轴区域"会打印明确警告，
并建议用 `--pos` 把悬浮窗挪开。

### 2.2 `WS_EX_LAYERED` 让悬浮窗变成**纯黑方块**

**现象**：用户看到"一个正方形不透明黑色"。

**根因**：`WS_EX_LAYERED` 让 DWM 把窗口当 layered 表面，而 Tk 用 GDI 绘制 → **合成结果是黑的**。
⚠️ **而且它不是我们加的** —— **Tk 的顶层窗口自己就带这个位**（诊断：句柄0 不含、句柄1 含）。

**修法**：**主动清除**这一个位（不是"不添加"）：
```python
cur = self.w32.ex_style(h)
self.w32.set(int(h), GWL_EXSTYLE, (cur & ~WS_EX_LAYERED) | bits)
```
**鼠标穿透只需要 `WS_EX_TRANSPARENT`，不需要 `WS_EX_LAYERED`。**

**为什么之前查不出来**：`PrintWindow` 读的是**窗口自己的绘制缓冲、绕过 DWM 合成** → 它看到的是正确的浅色卡片，而屏幕上是黑的。**截图证明不了合成问题。**

> ⚠️ 另一条同源教训：`BitBlt`/`mss` **抓不到 layered 窗口** → "截图里看不到悬浮窗"也**证明不了**它没显示。

### 2.3 深色配色在暗色游戏上 = 一块黑洞

**现象**：用户反馈"悬浮窗是纯黑"。

**根因**：背景 `#0e0e12`（约 6% 亮度）+ `alpha 0.85`，叠在**暗色游戏**上就是黑洞；
叠在**浅色界面**上却正常 —— 所以自测发现不了。

**修法（按用户实测反馈定案）**：
* **必须用浅底深字**（背景亮度 ~93% —— 用户实测：亮绿/亮青能看见，`#252a3d`(17%)、`#3d4463`(27%) 全看成黑）
* **不用 `-transparentcolor`**（Tk 键色抠图与 layered 叠加会画黑）
* **不用整窗 `-alpha`**（会把内容压成半透明黑）→ 默认 `alpha=1.0`

**当前配色**：`BG=#e9edf7`（浅灰白 ~93%）/ `FG=#141826`（近黑）/ 标题深橙 `#a8480f`。

## 3. 抓屏的三个坑

### 3.1 屏幕缩放 200% —— 不声明 DPI 感知就抓错地方（**最要紧**）

不声明时 `GetSystemMetrics` 和 mss **只报逻辑像素**（如 1440×900）→ 抓错区域。
**必须在创建 mss 实例之前**调 `capture.enable_dpi_awareness()`。

本机实测：物理 **2880×1800** / DPI 192 / 缩放 200% / 逻辑 1440×900。

### 3.2 这个工作区 `pip install` 装不了包

沙箱临时目录权限被拒。`mss` 用**下 wheel 解包到 `vendor/`** 的绕行方案（见 `install_mss_B.py`）。

### 3.3 `out/digit_cnn.onnx` 与 `.pt` 可能不是同一个模型

已加**防复发检查**：`hud_digits.check_model_freshness` 用探针
（`out/digit_cnn.probe.npz`，**argmax 必须全一致**）保证两条后端等价。

## 4. ⭐ 起手时序（**用户明确要求**）

> 用户原话："我用的时候是在**进战前开始的**，这样能保证所有的伤害能被记录，
> 但是你做的好像是**第一帧开始才能用**"

**含义**：正确流程是 **进战前就启动记录**，战斗一开始的伤害就都在采集范围内。

**由此推出两条硬约束**：

1. **开局不得阻塞等待定位**。
   原因：进战前**还没有伤害数字 → 没有墨迹 → HUD 定位必然失败**；若阻塞等待就会白等到打完。
   ⇒ 立即用**兜底框**开始记录；第一帧读到数字后由 `note_hud_result` 触发重定位。
   （`--wait-game` 默认 **3 秒**，只顺手试一次；进战前用可设 0）
2. **"读到数字"必须能触发重新定位**（已实现，别回退）：
   `ScreenSource.note_hud_result(ok)` → 连续失败则 `relocate()`；
   而 `relocate()` **只接受** `sa.hud_geometry()` 报 `src='ink'` 的结果
   （画面是桌面/聊天窗口时它会退回静态框，那个框不对，要**拒绝**）。

## 5. 悬浮窗实现要点（Windows）

| 需求 | 做法 |
|---|---|
| 置顶 | `attributes('-topmost', True)` + `WS_EX_TOPMOST` |
| **鼠标穿透** | `WS_EX_TRANSPARENT`（**不要** `WS_EX_LAYERED`，见 §2.2）|
| **不被自己抓到** | `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)`（见 §2.1）|
| 不抢焦点 | `WS_EX_NOACTIVATE` |
| 不进 Alt-Tab | `WS_EX_TOOLWINDOW` |
| **退出** | 全局热键 `Ctrl+Alt+Q`（`GetAsyncKeyState` 轮询，**每帧直查**，不依赖 Tk 定时器）；终端 `Ctrl+C` 也有效 |
| 调试可直接关闭 | `closable=True` → 不穿透 + 保留标题栏 → 能点 × |

⚠️ **DPI 感知必须先声明**再建窗口（同 §3.1）。
⚠️ `SetWindowLongPtrW` 必须设 `argtypes/restype`（不设时 ctypes 按 32 位处理 HWND，64 位下会**截断句柄**）。

### 悬浮窗显示内容（用户确认的规格）

## 6. ⭐ 定稿延迟（重要特性，不是 bug）

**悬浮窗上的数字比画面慢约 2.4 秒才"落定"**。
这是"口径与离线逐事件一致"的代价，**不是处理延迟**（处理 p95 只有 ~11ms）。

当前这一次攻击的读数会**实时显示在"当前行动"行**（未定稿段），但**不进合计**。
要缩短它就得改判据（重标 `frag/glitch` 窗口）→ **会动到线4 的口径**，不属 MVP。

### 8.2 怎么构建

```powershell

python build_exe.py --mode onedir --name HSR伤害统计 --readme out\交付说明_模板.txt

```

### 8.3 ⚠️ 打包的四个坑

| 坑 | 说明 |
|---|---|
| **`torch` 要两道保险才能摘掉** | `mvp/reader.py` 对 `read_hud` 的 import 已改**惰性**；spec 里还要 `excludes=['torch']`。不摘 → 体积 800MB~1.5GB |
| **资源路径一律过 `mvp/resource.py`** | 不许再写"相对当前目录"（打包后工作目录是任意位置）|
| **控制台编码：`print("✓")` 会把程序静默干掉** | 打包后控制台默认 GBK → `R.setup_console()` 先把输出切 UTF-8 |
| **入口是 `gui_main.py` 不是 `live_mvp.py`** | 双击弹**控制面板**；带参数时透传给 `live_mvp`（保持 `--selftest` 等行为）|

⚠️ **`--noconsole` 后看不到报错** → 保留一个"带控制台"的调试版命令写进文档。

## 10. 已知限制（诚实清单）

1. **定稿延迟 ~2.4 秒**（见 §6）。
2. **占比分母只含 `status == ok` 的事件** —— `review` 与 `non_ally` 都不进
   → **"合计"是下界，不是整局真值**。
3. **DPS / 每行动值伤害未实现**（`mvp/av_reader.py` 占位，恒显示 `—`）。
   前提是"行动轴卡片右侧那个数字是不是行动值"**尚未经用户确认**。
4. **多分辨率只做了"不写死坐标"的结构准备**，**没在别的分辨率上实测过**。
5. **实时模式下行动轴默认每 5 帧读一次**（每帧都抓会到 116ms，超预算）。
   E 线锚点允许 `±[-1.5s,+0.5s]` 借邻帧，量级一致。
6. **只做了单帧抓屏**：没有多局统计、没有 CSV 导出之外的历史、没有暴击/真伤区分。
7. **`out/live_calib.json` 是机器相关的**（分辨率 + 框 + 行带），已进 `.gitignore`；
   只影响"进战前启动的头几秒"，5 秒一次的画面复核会纠正任何过期标定。
8. **独占全屏下桌面悬浮窗可能看不见** → 建议游戏用「**窗口化全屏 / 无边框**」。
   ⚠️ 这条**没有自动化证据**（本机验证时前台是另一个独占全屏游戏，
   `mss` 抓的画面里不含悬浮窗，所以截图证明不了）。
