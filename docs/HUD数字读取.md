## 1. 管线（逐环 + 参数来历）

### 1.1 掩膜

```python
m = (R > 225) & (G > 225) & (B >= 185) & ((R - B) > 25)
```

* 取的是**辉光层**，不是笔画核心 —— 辉光层笔画**连续**，最利于列分割
* ⚠️ `B >= 185` 是关键：数字的**笔画核心本身是饱和黄**（`min(R,G)-B≈95`、B≈150），
  淡黄只是外圈辉光。这个阈值才能把 HUD 数字层与画面里的伤害飘字分开

### 1.2 字形灰度值（黄度）

```python
warm = np.clip(np.minimum(R, G) - B, 0, 255)
warm[~m] = 0
sub = warm[rows0:rows1+1, x0:x1+1]
sub = sub / max(1.0, float(sub.max()))      # ⚠️ 按字形自身峰值归一化，不是除以 255
```

**为什么必须按峰值归一化**：黄度原始值只有 **40~63**，直接除以 255 会把字形信息压扁。

### 1.3 断粘连（`BAR_ROWS`）—— **最容易忽略的坑**

```python
BAR_ROWS = (298, 310)      # 数字左侧那条细横线所在行带
ms = m.copy()
ms[BAR_ROWS[0]-CY0 : BAR_ROWS[1]-CY0+1, :] = False   # ⚠️ 只在**分割时**挖空
```

* 那条细横线是 **UI 元素**，会把**开头的几个数字粘成一大块** → 长数字一次丢好几位
* **只在分割时挖空；取字形时仍用完整掩膜 `m`**
* ⚠️⚠️ **`bar_rows` 必须与裁剪框成对**：框平移了而 `bar_rows` 没跟着平移（或反过来），
  挖空带就会压在数字自己的笔画上 → **字被切碎、丢前导位**。这是本项目栽过多次的坑

### 1.4 列分割

1. 逐列 `any` → 得到 run 区间；间隙 < 3px 的 run 合并
2. **链式连续性**：从**最右边**那个字形往左走，只保留与它连成一串的；
   中间隔了 **>20px** 的一律视为别的 UI 元素
   *实测依据*：`t=311` 左边 78px 外有杂散块，不剔除会平白多出一位
3. **加「段宽/墨迹跨度」安全网**：实机曾把画面上的 `630911` 自信地读成 `1`
   → 现在这种明显不合理的段判可疑，**不给数**
4. 过滤碎块与细横线：

```python
keep = (max(6, int(0.30 * h)) <= w <= 52) and (h >= 30)
```

* `W_MAX = 52`、`H_MIN = 30`
* ⚠️ **`H_MIN` 从 42 改成 30 的来历**：`H_MIN=42` 会**误杀窄字形 "1"**
  （"1"的辉光高度只有 31~37px）→ 改 30 后位数判定才达到 12/12

### 1.5 归一化与分类

```python
GW, GH = 24, 34
sub → resize((GW, GH), BILINEAR) → /255.0 → CNN(1×34×24) → 0~9
```

网络：`Conv(1→16,3×3) → pool → Conv(16→32) → pool → Conv(32→32) → pool → FC(32*4*3→64) → FC(64→10)`，
带 BatchNorm + Dropout(0.3)。

> ⚠️ **改裁剪/掩膜参数时，训练（`digit_dataset.py`）与推理必须同步** ——
> 现在两边都调 `hud_glyphs.py`，**同步是结构上保证的**（不再靠人记）。
> **`hud_glyphs.py` 是掩膜/分割的唯一实现**（训练、离线、实时三方共用）。

## 2. 多帧投票

```python
# 先按「位数众数」锁定位数，再在同样位数内逐位投票
cnt = Counter(len(s) for _, s in readings)
L = cnt.most_common(1)[0][0]
picked = [s for _, s in readings if len(s) == L]
final = 逐位取 Counter 的 most_common(1)
```

⚠️ **教训：不要"优先采信位数更多的读数"**。
曾以为"分割只会截断、不会多造字"，结果被偶然多切出一位的杂散读数带偏
（`1116982` 压过正确的 `721193`）→ 改成"**位数取众数**"才稳。

同一数值会停留（实测 ≈0.5s）→ 多帧投票能把随机误差压掉。
**单帧永远不可能 100%；多帧投票是提高最终准确率的关键。**

## 3. ⭐ 形近字缺陷的根因与修法（**本项目最有价值的教训**）

### 3.1 现象

`t=275` 期望 `904004` 读成 `904096`（0↔9、0↔6 两位错）；
`t=226` 期望 `49065` 读成 `49045`（**6↔4**，5 帧全错 → 投票救不了）。

### 3.2 根因：**掩膜把笔画核心掏空了**

掩膜 `(R>225)&(G>225)&(B>=185)&((R-B)>25)` 取的是**淡黄辉光层**，
而笔画核心是**饱和黄**（`min(R,G)-B≈95`、`B≈150`）→ **被 `B>=185` 排除**。
某些帧辉光一弱，笔画就被掏空成碎片。

**判据**：出错字形实测只有 **23px 宽**，正常是 **29~33px**。
⇒ **"读错内容"几乎总是字形提取问题，不是分类器问题。**

### 3.3 修法（唯一实现在 `hud_glyphs.py`）

* **列分割**仍用**辉光层**（实测最稳，96% 可用）。改用"核心∪辉光"做分割会**掉到 68%**
  —— 它把背景金线也吃进来，金线与最左数字粘成超宽块，反而整段丢数字
* **字形像素**改用 `fill_holes(辉光 ∪ 饱和核心)` 并**去掉背景金线**（长横条检测）
* 判定通过后，用完整字形掩膜向外**扩 ≤3px** 找回被弱辉光切掉的边缘

### 3.4 三个陷阱（**后来人别再踩**）

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| **外扩参与了有效性判定** | 判定标准被污染 | 外扩只在**取字形**时用，**不参与**判定 |
| **判定用了完整字形几何** | 高度 54→61、宽度下限 `0.30*h` 从 16 抬到 18 → **16px 宽的窄字形 `4` 被误杀** | **有效性判定必须用「辉光几何」** |
| **固定阈值反复误杀窄字形** | 调一个就杀另一个 | 已改成**自校准判定**（按本串自身的墨迹分布定阈） |

### 3.5 结果

留出集 **29/29 逐字、5/5 整串**；修复后 **5 个 seed 的单模型全部满分**。
`49065`、`904004` 均已读对。

**⚠️ 一条被推翻的旧结论**：文档曾写"补样本无效（44→107、成绩纹丝不动）"——
那是评测了**未重训的旧模型文件**（`eval_holdout.py` 读 `out/digit_cnn.pt`，当时只重建了数据集）。
反证：同一份 44 样本、只换训练配置（`bs=64`/140 epochs），留出集就是 29/29、5/5。
**那个 89.7% 主要由单次训练的随机性主导** → 所以现在交付**集成**模型（9 seed 平均 logits）。

**唯一仍不可靠的**：`t=102`（`3`+`0` 粘连成 75px 宽块被 `W_MAX=52` 整块丢弃）——
属已知的**单帧分割**问题，多帧投票可覆盖。

## 4. 第二种字体（银狼999 的像素方块字体）

### 4.1 机制：**按行动者切档，不从图像猜字体**

用户确认（2026-09-30）：**像素风的数字只在银狼999 的强化普攻出现**。
⇒ 不需要从图像猜字体 —— 让**行动轴告诉我们"现在是谁在打"**，直接选字体档案。
比任何图像启发式都可靠。

**档案表**（`hud_profiles.py`）：

| 档案 | 掩膜 | box | 几何范围 | 模型 |
|---|---|---|---|---|
| `default` | `glow`（淡黄）| `(260,2350,340,2876)` | 高 50~95 / 宽 14~60 | `digit_cnn.onnx` |
| `yinlang999` | **`cyan`（青色）** | `(250,2400,360,2870)` | 高 40~100 / 宽 18~80 | `digit_cnn_yinlang999.onnx` |

**一种字体 = 一套「区域 + 掩膜 + 分类器 + 几何范围」，不能共用。**

### 4.2 接口（三个函数，可直接 import）

```python
import hud_profiles as HP
from read_hud import read_for_actor, read_array_for_actor, vote_frames_checked

HP.profile_for_actor("狼尊")   # -> "yinlang999"
HP.profile_for_actor("遐蝶")   # -> "default"
HP.profile_for_actor(None)     # -> "default"

r = read_array_for_actor(frame_rgb, actor="狼尊")
# r["verdict"] = "ok" | "待复核"；"text"（待复核时为空串）；"profile"；"actor"
# r["n_glyphs"]（切出的字形数，可判断"这段确实是另一种字体且字形切得出来"）
# r["label"]；r["reason"]（待复核原因，人话）

r = vote_frames_checked(model_for_profile, frames, profile="yinlang999")
# 额外返回 "share"（逐位最低胜率）、"geom_bad"、"reasons"
```

**接线方式**（行动轴侧）：把行动者传进来即可，不需要知道字体细节。
`verdict != "ok"` 时**不要当数值用**，记 `待复核`。

### 4.3 加一种新字体要什么

最小素材 = **一张能看清数字的截图**（不用等录屏）。四步：
① 定位数字区域 → 填进 `hud_profiles.py` 新档案；
② 确认颜色/掩膜是否适用（原图/辉光掩膜/字形掩膜三联图）；
③ 出图给用户读 10~12 个数值 → 写进该字体的真值表；
④ 训分类器 + 留一帧验收。

> ⚠️ 已知缺口：`--profile` 参数**尚未接到** `digit_dataset.py` / `train_digit_cnn.py` 上。

| 项 | 值 |

| 来源帧 | **19 个** |

```python
{100:"121418", 109:"48076", 106:"2809", 102:"304505", 135:"191176",
 134:"47794", 152:"324751", 167:"113891", 195:"319195", ...}
```

⚠️ **`t=102` 实际被丢弃**（期望 6 位但只切出 3~4 段 → 建集逻辑认为"缺位无法确定缺左还是缺右"，
**宁可不收，避免贴错标签**）。但 `read_hud.py` 自检仍把它算进分母 →
**那个"单帧 8/9"里的 1 个错就是它，这一帧本身不可靠，不要当训练/验收依据。**

**训练配置**：
* 增强（必需）：位移 ±16% / 缩放 0.88~1.12 / 旋转 ±6° / 亮度对比度 /
  形态学（模拟辉光厚薄）/ 高斯噪声 σ=0.05
  *为什么必须增强*：同一数值停留期间有**出现动画**（缩放/透明度渐变）；有**两种字号**；
  字形带**金色辉光**且厚度逐帧不同
* 类别不平衡 → `CrossEntropyLoss(weight=...)` 按频次反比加权
* 最终：400 epochs, seed=7，全量数据；留一帧交叉验证用 260 epochs

**评估铁律**：
1. **只用"留一帧交叉验证"** —— 同一帧的字形不允许跨训练/测试集
2. 最诚实的评测是**从未参与训练的留出帧** → `eval_holdout.py`
3. `HOLDOUT = {226:"49065", 261:"721193", 275:"904004", 284:"111860", 311:"379852"}`

## 7. 排除掉的方案（**不要重试**）

| 方案 | 失败原因（实测） |
|---|---|
| **在线 VLM** | 会**凭空编造**（造出 `123456789`、`1480776`；把 `107023` 读成 `1107023`）；单次 2~4s，**违反实时硬需求** |
| **通用 OCR**（RapidOCR）| `48076` 读成 `94087` |
| **模板匹配 / 手工二值 XOR** | 最好只有 **70%**，多数 20~50%；对出现动画/双字号/辉光厚薄不鲁棒 |
| **字形聚类**（早期路线）| 聚类结果需人工认领，效率低；但其 `frame()` **抽帧函数仍被复用，别删** |
| **"优先采信位数更多的读数"** | 被杂散读数带偏（`1116982` 压过正确的 `721193`）|

**结论：固定字体 + 固定位置 + 颜色可分离 → 必须走本地分类器。**

## 4.4 ⚠️ 像素字体的**已知缺陷**：相邻位会被粘成一块（2026-10-05）

**现象**（用户实机反馈）：狼尊强普的伤害没记录。切到 yinlang999 档案后实测三张
用户确认过真值的像素帧：

| 帧 | 真值 | 档案切换后读出 | 结果 |
|---|---|---|---|
| t=238 | 123692 | 123692 | ✅（置信 1.00，6 字形）|
| t=100 | 506286 | 只切出 5 字形 | ❌ 位数少 1 |
| t=200 | 2052321 | 切不出字形 | ❌ |

**根因（量化）**：不是分类器不行，是**分割**。
hud_glyphs.cyan_mask 找的是青绿填充，而像素数字其实是**白色实心**；
更关键的是**相邻两位会被粘成一个宽块** ——
实测 t=100 出现 w44/h76、t=238 出现 w45/h86（单字应 h≈50）。
_split_wide_off() 目前**有意不拆**（历史上拆错过），于是
**字形数少 1 → 读数值与真值不符**。

**要彻底修好需要**（独立任务）：
1. 调 cyan_mask 或加白色实心通道；
2. 实现可靠的宽块拆分（按 CYAN_ADVANCE=59 的字距推断应拆几位）；
3. **必须重训 + 重新验收**：out/digit_dataset_yinlang999.npz（74 样本），
   基线**留一帧 70/74 = 94.6%**、集成 **14/15 整串** —— 改完不许低于它。

**已完成的**：实时链路现在**会**按行动者切档案了（mvp/reader.py 的 profile_for
+ HudOnnxReader(profile=...)）。所以**像素字体那一路终于接上了**，
只是分割精度还不够 —— 这一条从完全没接变成接了、部分帧读不准。
