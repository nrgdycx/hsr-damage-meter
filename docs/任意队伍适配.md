> 用户目标（原话）：**"我需要识别是哪些角色"**。
> 结论：已做成一条**可复制的四步流水线**——用户给一段战斗录屏 → 系统自动挖出场上角色的

>
> **验收全部达成**（含用录屏2 复现当年纯人工的 98.8%，逐条一致）。

## 1. 四条命令（这就是全部工作流）

```powershell
cd D:\project\hsr-damage-meter
$env:PYTHONIOENCODING='utf-8'

# ① 抽帧：录屏 → 顶端卡小块 + 一张"队伍面板全帧"（画面上带角色名，指认时要看它）
python axis_onboard.py extract --video "records/xxx.mp4" --team 我的队 --step 2 --end 360

# ② 自动分组：把"长得一样"的头像归成组
python axis_onboard.py cluster --team 我的队

# ③ 出指认图 + 答案模板（用户只做这一步）
python axis_onboard.py label   --team 我的队
#    → 看 samples/我的队_请指认.png（队伍面板在最上面，照着一遍读完）
#    → 填 out/teams/我的队.labels.json 的 _answers：{"1": "银狼", "2": "火花", ...}

# ④ 建库 + 自检
python axis_onboard.py build   --team 我的队
python axis_onboard.py eval    --team 我的队
```

**之后实时就能认这些角色了** —— 因为模板进了 `out/axis_top_bank_E.npz`，
而实时链路（`mvp/reader.py` → `axis_actor.load_bank()`）读的就是这个文件。
源码运行**立即生效**；打包版需要重新跑 `python build_exe.py`（spec 会把 npz 打进包）。

> 🔎 为什么"所有角色进同一个库"而不是"每支队伍一个库"：用户的原话是
> **"跟队伍没关系，我需要识别是哪些角色"**。所以适配的粒度是**角色**，
> 队伍只是"若干角色名的清单"（登记在 `out/teams/index.json`）。
> 同一角色在多支队伍里**只挖一次模板**，全项目共享。

## 2. 用户唯一要做的判断：看一张图报名字

`samples/team2_请指认.png`（1650×2540，一屏内）：
最上面是**队伍面板**——游戏画面上**直接写着角色名**，照着念即可；
下面是每个自动分组（组号 + 帧数 + 3 张样本，含"组内最不像成员"以便发现"这组混了两个人"）。

指认完的答案长这样：

```json
"_answers": { "1": "银狼", "2": "火花", "3": "爻光", "4": "真珠",
              "5": "银狼", "6": "银狼", "8": "火花" }
```

* **同一个人的多个形态，各填同一个名字** → 这些形态的模板都进该角色的库（这是必要的：
  银狼在行动轴上有"眼镜放头上"和"戴着眼镜"两种形态）。
* 不是角色的组（敌方差/特效/过渡）**留空**即可，默认跳过。
* 默认只把"左标记=我方单位卡"的帧拿去分组（实测 84 个真值帧 **100%** 被判成 `ally_*`），
  所以阿哈面具框/敌方卡不会来烦用户；覆盖率偏低时会明确告警并回退全集。

## 3. 需要澄清的一件事：**跨形态认不出来**

评估故意报**两个口径**，因为"留一帧"在本项目里其实是两件不同的事：

| 口径 | 做法 | team2 实测 | 含义 |
|---|---|---|---|
| ① 逐帧留出 | 只把该帧自己的模板拿掉（同组近邻**仍在**库里）| 63/65 = 96.9% | **自洽性**，用来与当年 98.8% 横向对比 |
| ② 逐组留出 | 该形态**整组**拿掉，只靠库里别的形态/角色认它 | 7/65 = 10.8% | **真实泛化**能力 |
| 外部真值 | 用当年人工核对的 84 帧、全库直接认 | **83/84 = 98.8%** | 与当年**逐条一致** |

**结论**：这套 NCC 特征匹配**不会**把"同一个人的另一个形态"认出来
（实测：留着"眼镜放头上"的模板去认"戴着眼镜"的帧，分数只有 0.5 上下，远低于 0.90 闸）。
所以——

> ✅ 正确用法：**把该角色在战斗中出现的每个形态都在指认图上报同一个名字。**
> ❌ 不要指望只标一个形态就自动泛化到另一个。

这不是缺陷而是**取舍的必然**：项目铁律是"宁可漏，不要错"，而把阈值降到 0.5
去强行跨形态匹配，会立刻把敌方卡/特效卡放进来（当年正是因为这一点才把闸设在 0.90/0.45）。

## 6. 性能与实时链路

**实测（本机，12 角色 / 136 帧模板）**：

| 路径 | 耗时 | 说明 |
|---|---|---|
| 裁块路径（抓屏 → 裁顶端卡 → 识别）| **12.3~13.9 ms/帧** | 实时 30fps 走这条 |
| 整帧路径（含线7 动态定位 + 标记 + 特征）| **20.6~21.1 ms/帧** | 硬需求 100 ms → **余量约 4.7×** |

🔍 **一个反直觉但重要的实测结论：耗时与"库里有多少角色"基本无关**
（12 角色库 21.06 ms/帧 vs 当年 4 角色库 23.69 ms/帧，后者反而略慢）。
所以耗时的大头是**线7 的动态定位与标记匹配**，不是模板匹配；
"角色越挖越多会拖慢实时"这个担心在当前规模下**不成立**（§9 第 5 条据此更新）。

接法**不需要改任何识别代码**：`mvp/reader.py` 已经用 `T.load_bank()`，
而 onboarding 写的正是同一个 npz。唯一注意点：**打完包要重新 `build_exe.py`**，
否则 exe 里的 npz 还是旧的。

### 7.1 ⭐ 工作方式铁律（用户 2026-10-02 明确要求，代价很大才换来）

> **信息不足时，先把图摆给用户看，让用户用眼睛判断；不要自己闷头连试 N 轮再下结论。**

来历：在"官图能否当模板"这件事上，我连续做了 10 轮数值实验（灰度/边缘/梯度/色相直方图/
统一变换/裁剪窗口/竖向带/二维搜索…），每轮都自己判定"失败了"，**却始终没有把对比图摆给用户**。
用户的原话是：

> "不是你倒是把你觉得不对的给我看啊，你就是一直自己搞，你把对比图给我看我才知道问题在哪啊"

代价：① 我用了**错误的银狼 id**（`1006` 普通银狼，而不是 `1506` **银狼LV.999**）跑了多轮，
结论自然错；② 我一度用 t=164 那帧当"风堇"，那其实是她旁边的忆灵**小伊卡**；
③ 用户早就知道"某角色皮肤不同、某形态不同"，但因为我没给图，这些信息一直没机会进来。

**正确做法（写进流程）**：
1. 只要结论依赖"看"，就**先出对照图**（并排 + 放大 + 标出我认为不对的位置），再谈数值；
2. 自己不确定的配对，**在图上标出来问用户**，而不是猜；
3. 需要用户提供事实（哪个 id、哪张对哪张、哪帧是谁）时，**一次问清**，不要分十轮挤牙膏。

## 13. 第三段录屏（164043）实战：抽帧提速 20×、GBK 崩溃、以及一个**关键限制**

素材：`records/屏幕录制 2026-10-03 164043.mp4`（12 分 26 秒、2880×1800、21 Mbps）。

```
python tools/axis/harvest_characters.py --video "records/屏幕录制 2026-10-03 164043.mp4" --team <队名>
```

### 13.1 修掉的两个真 bug

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 逐帧 `-ss` seek **1.19 秒/帧** → 12 分钟录屏要 **74 分钟** | 每次 seek 都要从关键帧解码（21 Mbps 2880×1800） | 新增 `--mode fast`（默认）：**整片一次解码 + `crop` 只切"标记+卡"那一小块**。实测 3730 帧全流程（含聚类/认名/出图）**2.5 分钟** |
| 2 | 扫完、聚类完，**最后打印分栏时崩** `UnicodeEncodeError: 'gbk' codec can't encode '\u26a0'` → 图一张没出 | Windows 控制台默认 GBK，`⚠` 无法编码 | `main()` 里 `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` |

⚠️ 这个精简版 ffmpeg（remotion 自带）**没有 `fps`/`select` 滤镜**，只有 `crop`/`scale`/`concat` 等；
降采样只能用**输出选项 `-r`**（实测可用）。用 `-vf fps=...` 会报 `No option name near`。

### 13.2 认名闸必须收紧（否则会输出**错的**名字）

本录屏 1055 张卡对全库 36 个角色的最高分：**中位 0.93、最大 1.25**——
**没有任何一张达到 1.45**。而原 `NAME_THR=0.85` 会把 0.9~1.1 的"最像谁"当成结论输出：
实测输出了 17 个名字（艾丝妲/丹恒·饮月/老杨/砂金…），**逐张看图核对，它们和旧录屏里同名角色
根本不是同一个人**（samples/诊断_同名对照.png：左=本录屏被命名的卡，右=旧录屏真值同名的卡）。

⇒ `NAME_THR` 默认改为 **1.45**（旧录屏实测"认对"是 1.70~1.90，留有余量）。
分不清就**弃权**，符合"宁可漏不要错"。

### 13.3 未认出的卡不能挤成一栏

原来所有认不出的卡进**同一个**「新角色？」栏（本录屏 804/1055 张 = 76%），
用户面对一栏 800 张杂卡**无法回答**。现在对未认出的卡**再用更严的阈值聚一次**，
各自成栏（`【新角色? #k】`，标"最像谁"），一栏一个人。

### 13.4 ⚠️ 本轮最重要的发现：同一个人会落在不同位置/背景（**卡的框不动，框内头像会动**）

这是本次"自动分组不可靠"的根因，且有可复现的测量：

| 事实 | 测量 |
|---|---|
| 同一场战斗内、同一角色的卡（我逐张看图确认是同一人） | 原始分只有 **1.19~1.41**，而"同一个人"应该是 **1.9** |
| 允许 **2~8 像素位移**后重测同一个人 | **1.55 / 1.69 / 1.74**（V19/V26 从 1.22 → **1.74**，位移 +8+4） |
| 不同的人怎么对齐 | 仍然只有 **0.30~0.68** |
| 差异图（samples/诊断_同人异分.png） | 头像是**同一张画**，但位置差 2~8px、卡的背景色不同（蓝 vs 金） |

原因：顶端那张"当前行动者"的卡里，**人物画带"弹入/位移"动画**（见 §13.6 的逐帧测量：
卡框本身在所有帧上都固定不动，动的是框里那张头像）；卡的背景是半透明/随环境变，
也会跟着变。现有特征是 4 张 72×48 归一化图，对 1~2px 位移极其敏感（项目早期就记过"差 1px 就塌"）。

**后果（诚实结论）**：

* 跨录屏/跨战斗的自动归并**不可靠**：同一个人 1.0~1.5，不同的人 0.9~1.0，**两带重叠**；
* 因此本录屏无法自动输出"按角色名分栏"的可靠结果；
* 但**同一场战斗内**同一个人的卡几乎相同（组内最低分中位 **1.58~1.87**），
  所以"按战斗场次 → 每场几个稳定长相"是**可靠**的。

试过但**无效**的路（都已实测，别再走）：
中心裁小窗口（分离度反而更差）、高通滤波（-0.36）、中心加权（-0.24）、
FFT 幅度谱（平移不变，但不同人也能到 0.97）、卡的青色边框定位（卡自带背景就是青绿，掩膜被污染）、
卡右上 ✕ 图标定位（基准卡上根本没有亮图标）、动态定位 `geom_for`（返回的框与静态框完全相同）。

⇒ 解法**不是**"把卡对齐"（见 §13.6：**框是固定的，没有可对齐的锚点**），
而是**让打分容忍位移**。已实现，见 §13.6。

### 13.6 修法：位移容忍打分（已实现，效果决定性）

#### 先纠正我自己的一个错误假设

我原以为是"整张卡在滑入"，于是试了用卡框对齐（青色边框定位、✕ 图标定位、
1055 张卡的**平均边缘图**做模板）。**全部失败**，因为前提就是错的。
用 `geometry.axis_geometry(refine=True)`（让画面证据顶掉模型）逐帧量了一下：

```
t=575.60   left=88.0  top=80.0   card=(88,80,283,175)
t=596.60   left=88.0  top=80.0   card=(88,80,283,175)
t=511.20   left=88.0  top=80.0   …（整段录屏都一样）
```

⇒ **卡的边框在所有帧上都不动**，动的是**框里那张头像**：卡是一个固定窗口，
里面的人物画带"弹入/位移"动画。所以"按框对齐"无处可依。

（副产物：`samples/诊断_平均边缘图.png` —— 1055 张卡的平均边缘图里，卡框 / ◀ / ✕
这些与角色无关的结构会**显形**，角色图案被抹平。它是很好的对齐模板来源，
只是既然框不动，这里用不上。）

#### 改的是**打分方式**

```
score = max_{|dx|,|dy| <= R}  Σ_c w_c · mean(f_c · shift(m_c))
```

用 FFT 一次算出所有位移的互相关、只需**一次逆变换**，成本几乎不增加
（实测 **0.15~0.2 ms/对**；1055 张卡全对全约 1~2 分钟）。

`tools/axis/harvest_characters.py` 新增 `feat_fft()` / `pair_score_shift()`；
`cluster_cards()` 与 `tools/axis/battle_sheet.py` 都改用它们（`SHIFT_R=5`
特征图像素 ≈ 10 原像素）。

#### 单元验证（可复现）

| 情形 | 位移容忍 | 位置敏感（旧） |
|---|---|---|
| 自身 | **1.900** | 1.900 |
| 平移 1 像素 | **1.900** | 1.688 |
| 平移 3 像素 | **1.900** | 1.269 |
| 平移 6 像素 | **1.688** | 0.927 |
| 平移 10 像素 | 1.037 | 0.576 |

自比仍是 **1.900**（尺度不变）⇒ 1.45 / 1.30 这两条线不用换算。

#### 端到端效果（同一段录屏、同一批 1055 张卡）

| 指标 | 修前 | 修后 |
|---|---|---|
| 每场战斗的"长相"数 | 4~9 个（大量是同一人被拆开） | **3~4 个**（正好一支队伍） |
| 全局分组数 | 53~74 组 | 45~47 组（阈值 1.0~1.3 之间是平台） |
| 跨战斗的同一个人 | 1.0~1.5 | **1.4~1.55** |

#### 仍然没解决的部分（诚实）

跨战斗的同一个人最高只到 **1.4~1.55**（同一场战斗内是 1.6~1.9），
原因是**卡的背景/环境色随战斗场景变化**（差异图见 `samples/诊断_同人异分.png`）。
本录屏 11 场 × 4 ≈ 44 个位置、全局聚出 39~47 组，**无法只从数据上确定它们是
"44 个不同角色"还是"同一批角色被场景差异拆开"** —— 需要用户的真值（报名字）才能定论。

把这条做实的下一步：同一角色在不同场景下的**颜色/背景归一化**；或改用对背景不敏感的
特征（本轮试过高通、中心加权、FFT 幅度谱，**都无效**，见 §13.4）。

⚠️ **本轮只改了 harvest 这条离线链路；实时识别器 `axis_actor.py` 未动**
（它用的同样是位置敏感的点积，同样受这个影响）。要动它必须单独跑
`eval_holdout.py` / `axis_actor.py --selftest` / `events_v4.py --anchors`
三条回归，并重标定 0.90/0.45 两道闸 —— 那是另一件事。

1. **组 ↔ 身份的对应不能用"组内第一个成员的时刻"**到就近匹配 —— 那个成员不是按时间排序的，
   实测 8 组 / 250 张卡对不上身份，只建出 27 个条目。正确做法是与 `battle_sheet`

2. **相似度矩阵必须与出表时完全同口径**（含放大态补偿的 max）。我一开始只用了原态，

### 13.10 匹配向量化：整帧 71.9 ms → **28.4 ms**（为"收齐 100+ 角色"腾出预算）

库涨到 98 条目 / 2188 张模板后，整帧识别涨到 **71.9 ms** —— 100 ms 预算已被吃掉七成，
**按这个斜率收齐 100+ 角色会超额**。原因是 `match()` 是**逐单位**做 4 次归约，
开销随**单位数**（不是模板数）增长，98 个单位 × 4 次 numpy 归约 → 单位多了就慢。

改成：把所有模板拼成一个大矩阵（缓存一次），一帧只做**一次矩阵乘**，再按单位取最大值。

```
分数 = Σ_c W_c·mean(m_c·f_c) − zoom折扣
     = dot(√W ⊙ m, √W ⊙ f) / 3456 − pen        （把权重折进两边，等价）
```

* **等价性**：与原实现逐单位比对，最大偏差 **5.96e-07**（float32 舍入）；
* **单帧匹配 5.9 ms**；**整帧识别 28.4~29.1 ms/帧**（改前 71.9 ms）；
* 三条回归全绿：`eval_holdout` 29/29、`axis_actor --selftest` 18+3 全一致、
  `events_v4 --anchors` 10/0/8；
* ⇒ 按 28 ms / 2188 模板推算，100 ms 预算可容纳 **~8000 张模板 ≈ 190 个身份**，
  足够覆盖"98 个可玩角色 + 93 个皮肤/变体"。

⚠️ 这条改动**动了实时识别器**，所以必须跑上面三条回归（已跑，全绿）。
`T.match()` 的返回格式与语义（每单位的最好/次好、zoom 折扣）**未变**。

### 13.12 召唤物为什么会被漏：**质量闸把"平滑的金龙"当成了空槽**

用户问"盾丹的召唤物呢"。查下来根因是**梯度闸**：

| 帧类型 | 梯度中位 | 90 分位 | 最小 |
|---|---|---|---|
| 空槽/非战斗 | **0.2** | 7.8 | 0.0 |
| 我方角色卡 | 17.4 | 19.8 | 10.0 |
| **龙灵（金龙，盾丹的召唤物）** | — | — | **6.9~10.6** |

`GRAD_MIN = 12.0` 卡在"我方卡最小值 10.0"之上，于是**龙灵这种一大片平滑金色的召唤物
被判成空槽丢掉**（它的**标记闸是过的**：`ally_dot`）。已把 `GRAD_MIN` 放到 **6.5**
（空槽那侧本来就被标记闸挡着——`empty/none` 不以 `ally` 开头）。

"按顺序对位碎片"会把名字贴到别的卡上（实测把「龙灵」贴到了 t=262 的灰发角色，
污染了一整个条目）。所以碎片改成 **`[时刻, 库条目名]` 显式指定**，未列出的未归属卡
一律**自动匹配**、认不出就报出来。

### 13.17 第三段网上素材（`皮肤.mp4`）：拼贴/演示视频要换通道

用户给的是**皮肤演示视频**（画面里有"160元风堇皮肤实机演示"标题、"＋关注"按钮、
"记忆/风堇"展示界面），而且**是多段拼接**：每段的黑边宽度都不同
（实测同一文件内上边在 12/48/92/248 之间跳）。

**踩到并修掉的三件事**

1. **黑边判据不能看亮度**：暗场景会被当成黑边。改成「**纯黑且行/列方差≈0**」
   （真实信箱边是渲染出来的纯黑）。判据写在 `T.crop_letterbox`。
2. **全黑帧会把整幅判成黑边** → 裁出空图，`cv2.resize` 直接崩
   （`!ssize.empty()`）。加保护：裁完小于 64×64 就**原样返回**。
3. **快通道对拼贴视频无效**：它整段只探一次黑边（`probe_bar`），拼贴里每段不同 ⇒
   第一遍只采到 9 张。这段改用 **`--mode seek`（逐帧裁边）** 才对：
   `harvest_characters.py --mode seek --step 0.5`。
4. ⭐ **2026-10-05 补的第 4 件（"伪黑边"）**：原来只要**任意一侧**出现 ≥`min_bar` 的黑边
   就整体裁剪 → 暗场景/转场时边上那圈 **8~12px** 的暗条也会触发，
   把图**整体裁歪几个像素**。后果分两种：
   * 自己定位那条路：几何按**裁后**的图算，模型假定内容顶在图上边 → 卡框偏掉 →
     认得出的卡变"待复核"（`axis_actor --selftest` 里唯一那条红点 `t=159` 就是它，已修）；
   * **调用方给了 `geom`** 那条路更糟：图的原点变了、几何没变 → 卡框整体错位，
     严重时几何比图还大 → `top_art` 抛 `帧尺寸 (88,280) 太小` → **实机闪退**
     （这就是 §2.1 的真凶）。
   ⇒ 修法两条：判据改成**逐侧**判（`min_bar*step = 16px` 以下按"没有黑边"处理）；
     `read_actor` 里**只有自己定位（`geom is None`）时才裁**。
   真正的信箱边是 **80~90px** 量级，远大于 16px，所以这不影响原来要修的场景。

⇒ 纪律：**素材是"拼接/演示视频"时一律走 seek 通道**；只有单一来源的连续录屏才用快通道。

  其中的 `遐蝶•巧思` 之类**不能当作皮肤名单**去追；
* 皮肤的**唯一可靠名字来源 = 用户**（库里 `风堇·云边拾暖`/`遐蝶·幽梦翩跹`/`绯英·月待花时`
  都是用户给的名字）；
* 因此"还缺哪些皮肤"**不能由数据推导**，只能等用户给素材时顺手给名字。
  之前所有"93 个皮肤/变体待收"的说法都应理解为**头像条目数**，不是皮肤数。
