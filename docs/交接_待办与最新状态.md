## 2. 闪退（§2.1）与像素字体（§2.2）

### 2.1 闪退的**根因** —— ✅ 已定位并修掉（2026-10-05 本轮）

**真根因：不是时序，是 `axis_actor.read_actor()` 里那句无条件的 `crop_letterbox(img)`。**

* 实时抓来的**已经是**轴区域（`capture.AXIS_REGION` = x60~340，**280×1260**），
  调用方传的 `geom` 用的就是这个区域**自己的坐标系**；
* `crop_letterbox` 又按画面裁一刀 → **图的原点变了、几何没变** → 卡框整体错位；
* 它的判据是"纯黑且方差近 0"（用来对付 `水砂视频` 那种真信箱边），
  而**暗场景/转场**很容易骗过它 —— 这在实机上是**常态**，不是罕见边界。

**关键证据**（1427 张真实整屏帧，逐帧实测）：

| 量 | 数 |
|---|---|
| 轴区域被 `crop_letterbox` 裁掉的帧 | **188 / 1427** |
| 其中"本来 1.90 分认得出 → 变成待复核" | **65 帧**（如 `f00109` 本该认出遐蝶） |
| 其中直接抛 `帧尺寸 (…) 太小`（= 用户看到的闪退） | **3 帧** |
| "整帧自定位"与"轴区域+局部几何"两条路不一致 | **19 → 1** |
| `axis_actor --selftest` 红点 | **1（t=159）→ 0** |

> ⭐ **钥匙是报错里的 `(88, 280)`**：`bgr.shape[:2]`，即"**88 行 × 280 列**"。
> 实时轴区域是 **280 宽 × 1260 高**，宽对得上、高只有 88 ⇒ **它根本不是原始轴区域，
> 是被裁过的**。原来那条"几何来自上一次定位"的推断因此是错的 —— 几何一直是对的。

**修法**（`axis_actor.py`）：
1. `read_actor`：裁黑边**只在自己定位（`geom is None`）时做**；
   调用方给了 `geom` 时图已在几何的坐标系里，**不许再裁**。
2. `crop_letterbox`：原来只要**任意一侧**出现 ≥16px 黑边就整体裁 →
   改成**每一侧单独判**，`min_bar*step = 16px` 以下按"没有黑边"处理。

**第 2 条顺带解释了那条唯一的回归红点 `t=159`**：
卡的屏幕位置没动，却被顶部 **8px 暗条**把原点裁下去 8px → 分数从 1.90 掉到 1.25
（期望长夜月，实得待复核）。**t=159 不是"边界帧"，就是这条 bug 的哨兵。**

**永久守卫**（都已进自检，会跟着 exe 一起跑）：
* `mvp/live_mvp.py --selftest` 新增第 **⑥** 条：轴区域顶部贴 **40px 纯黑**（模拟卡上方的暗带）
  → 读数必须**一个字不变**。旧代码实测：顶端 `死龙` 1.785 → 待复核 0.535。
* `axis_actor.py --selftest` 的 **t=159** 现在通过。
* `axis_actor.py --selftest` 另加**黑边裁决两向守卫**（2026-10-05 二轮）：
  ① 卡**上方**涂 20px 纯黑（伪黑边）→ 必须**不裁**（旧代码实测 待复核 0.855 ↔ 修后 遐蝶 1.900）；
  ② **上边贴** 20px 纯黑、内容整体下移（真信箱边）→ 必须**裁回**（否则判不出来）。

#### 二轮：离线 E 线那条残留也修了（2026-10-05）

残留症状：整帧自定位（离线 E 线）会被**伪黑边**顶偏，实测还剩 **1/1427**
（`frames/T1_rec1640/f00359.00.png` 左侧 32px 暗条：整帧路 0.799/待复核，实时路 1.890/刻律德菈）。

**先量了数据，结论是"纯几何阈值切不开"**：

| | 真信箱边（`水砂视频` / `皮肤.mp4`） | 伪黑边（真实游戏帧） |
|---|---|---|
| 上/下/左/右(px) | 92/88、**48/0（单侧！）**、92/0、12/24 | 8/0、16/24、**左32/0**、右152/0、下116/0 |

⇒ ⛔ **"两侧对称才算信箱边"是错的方向**（会毁掉 `皮肤.mp4` 的单侧 48px）；
大小也重叠（真 48 vs 伪 40/28）。**别走这条路。**

**真正分得开的是"裁完还过不过闸"**：
* 真信箱边：不裁 **过不了闸**（0.61~0.70）→ 裁后 1.70~1.89 **过闸** ⇒ 该裁；
* 伪黑边：两种**都过不了闸**（最高的也才 0.795），或本来就能过 ⇒ **不该裁**（不动坐标更安全）。

⇒ 新增 `axis_actor.self_locate()`：整帧输入时，**裁与不裁各按同一条闸判一次**，
"只有裁了才过闸"才裁，**平手一律不裁**（`crop_letterbox` 只在有黑边判定时才多算一次，绝大多数帧零额外开销）。

实测（1427 张真实整屏帧）：**两路不一致 1 → 0**（全一致）；
`水砂视频` 真信箱边 **4/4 仍正确裁切**并认出卡（1.795~1.892）；三条回归 + 实时自检 + preflight 全绿。

⚠️ 注意影响面：只改**整帧自定位**那条路（离线 E 线 / 收割脚本）；
**实时链路传 `geom`，根本不走这里**。已落盘的 `out/frames_dense4.csv` 等**没有重跑**
（它们是事件表的权威输入）→ 想吃到这个改善得单独验收后重跑线4/线8。

### 2.2 像素字体（狼尊强普）的**分割**不准

档案切换已生效，但用**用户确认过真值**的三张像素帧实测：

| 帧 | 真值 | 读出 | 问题 |
|---|---|---|---|
| t=238 | `123692` | `123692` ✓（置信 1.00）| — |
| t=100 | `506286` | 只切出 **5** 字形（应 6）| ❌ |
| t=200 | `2052321` | **切不出字形** | ❌ |

**根因（已量化）**：不是分类器，是**分割**。
`hud_glyphs.cyan_mask` 找的是"青绿填充"，而像素数字其实是**白色实心**；
关键是**相邻两位被粘成一个宽块** —— 实测 `w44/h76`、`w45/h86`（单字应 h≈50）
→ 字形数少 1 → 读数值不对。`_split_wide_off()` 目前**有意"不拆"**（历史上拆错过）。

**要彻底修好**：
1. 调 `cyan_mask` 或加"白色实心"通道；
2. 实现可靠的宽块拆分（可按 `CYAN_ADVANCE=59` 的字距推断应拆几位）；
3. ⚠️ **必须重训 + 重新验收**：`out/digit_dataset_yinlang999.npz`（74 样本），
   基线**留一帧 70/74 = 94.6%**、集成 **14/15 整串** —— 改完不许低于它。

### 命令

```powershell
cd D:\project\hsr-damage-meter

python preflight.py                     # ⭐ 实机/发布前自查（23 项）
python eval_holdout.py                  # 数字识别回归 → 期望 29/29 + 5/5

# 实机（建议进战前就跑）
#   双击 dist\HSR伤害统计\HSR伤害统计.exe → 点「开始统计」
#   日志：dist\HSR伤害统计\运行日志.txt（每 2 秒一行 [诊断]）
```

> ⚠️ **在受限 shell（例如 agent 的沙箱）里跑"无控制台" exe 的自检**：
> 直接 `& exe --selftest` 会**静默什么都不发生**（GUI 子系统进程继承父进程管道 → 卡住，
> 连 `运行日志.txt` 都不生成；`Start-Process -Wait` 也会一直挂着）。
> **必须把 stdio 重定向出去**才跑得起来：
>
> ```powershell
> $p = Start-Process -FilePath "dist\HSR伤害统计\HSR伤害统计.exe" -ArgumentList "--selftest" -PassThru `
>       -RedirectStandardOutput out\_so.txt -RedirectStandardError out\_se.txt
> $p.WaitForExit(120000)
> Get-Content "dist\HSR伤害统计\运行日志.txt" -Encoding UTF8 -Tail 5   # 期望「自检通过 ✓」
> ```
>
> 要看启动期 stdout（无控制台版看不到）就构建一个**带控制台**的诊断版（另存名字，别覆盖交付版）：
> `python build_exe.py --mode onedir --name HSR诊断 --console --no-zip`

### 实机日志怎么读（**用户报问题时先要这个**）

```
[诊断] 框来源=ink:120 ｜ 可信读数 45/180=25.0% ｜ 行动轴 判出行动者 60/180=33.3% ｜ 事件 5（待复核 2）
         ↑ 定位坏没有        ↑ 读数环节坏没有        ↑ 归属环节坏没有            ↑ 结果
```
* `框来源` 全是 `model:` → **定位坏了**（HUD 框没跟上实机）
* `可信读数` <10% → **读数环节坏了**
* `行动轴 判出行动者` <10% → **归属环节坏了**（可能就是 §2.1）
* 三个都正常但事件很少 → **切分口径问题**
